# Task 02 Proofs — Broadcast light theme and full AA contrast verification

## Task Summary

This task proves the light theme is a deliberately designed counterpart to the
dark theme rather than an inversion of it, and that **every** foreground/surface
token pairing in **both** themes meets WCAG 2.1 AA — measured, tabulated, and
enforced on every test run.

The spec named the light theme as the risk: it had no mockup, and the amber
accent that anchors the dark theme measures 1.9:1 on white. The owner declined a
light-theme design review, making the computed contrast report the sole
acceptance gate for this task.

## What This Task Proves

- All 124 token pairings across both themes meet their AA threshold, with zero
  failures.
- The light theme is designed, not inverted: warm paper ground, cards lifted to
  white, and an amber accent darkened to hold its hue family while clearing
  4.5:1.
- The contrast report is generated by the test suite, so it cannot drift from
  the values actually asserted.
- `ThemeContext` behaviour (FR U1-6) is preserved — the file is untouched across
  the entire branch.
- The matrix caught a real defect that hand-checking missed.

## Artifact: Full contrast matrix, both themes, zero failures

**What it proves:** FR U1-7 — every text/background pairing meets AA in both
themes.

**Why it matters:** This is the acceptance gate for the light theme. With the
design review waived, these numbers are the only thing standing between the
palette and an unreadable light mode.

**Command:**

```bash
cd frontend && npm run test
```

**Artifact path:** `docs/specs/01-spec-broadcast-foundation-shell/artifacts/contrast-report.md`

**Result summary:** 124 pairings measured across both themes — 10 foreground
tokens × 6 surfaces × 2 themes, plus 2 control-border checks per theme. All
pass.

```
- Pairings measured: **124**
- Passing: **124**
- Failing: **0**
```

The tightest margins in the entire matrix are the control borders, all clearing
their 3:1 floor:

| Theme | Token | Surface | Ratio | Required |
| --- | --- | --- | --- | --- |
| dark | `--border-strong` | `--bg-card` | 3.19:1 | 3:1 |
| light | `--border-strong` | `--bg-page` | 3.30:1 | 3:1 |
| dark | `--border-strong` | `--bg-page` | 3.49:1 | 3:1 |
| light | `--border-strong` | `--bg-card` | 3.69:1 | 3:1 |

Every *text* pairing clears 4.5:1 with more room than that.

## Artifact: The matrix caught a defect hand-checking missed

**What it proves:** The enumeration is doing real work, not confirming a palette
already known to be good.

**Why it matters:** Before writing the matrix I had probed candidate values
against `--bg-page`, `--bg-card`, and `--bg-selected` — the three surfaces I
reasoned about. The matrix tests all six, including `--bg-subtle`, `--bg-hover`,
and `--bg-row-stripe`.

**Result summary:** On first run the suite failed on a surface I had not
considered:

```
FAIL  light > --success on --bg-hover meets 4.5:1
AssertionError: expected 4.34 to be greater than or equal to 4.5
```

Light `--success` was `#1a7f37`, which measured 4.50:1 on a selected row — just
passing — but 4.34:1 on a hovered row. In practice this is a green delta figure
in a table row under the cursor, which is exactly when someone is reading it. It
was darkened to `#16702e` and the suite went green.

This is the failure mode the audit's "regression-risk blind spots" gate was
pointing at: a palette verified against the surfaces a designer happens to think
of, shipping a failure on the one they did not.

## Artifact: Light theme is designed, not inverted

**What it proves:** The light theme applies the dark theme's logic rather than
flipping its values.

**Why it matters:** FR U1-3 explicitly requires "an equally considered light
theme rather than a naive inversion". An inversion is the cheap path and the
spec named it as the thing to avoid.

**Artifact path:** `frontend/src/styles.css` (`:root` block)

**Result summary:** The organising principle carries over — panels are separated
from ground by lightness — but applied in the correct direction for a light
surface, with a warm ground rather than the dark theme's blue-biased charcoal.

| Role | Dark | Light | Relationship |
| --- | --- | --- | --- |
| ground | `#0e1116` blue-biased charcoal | `#f4f2ef` warm paper | both recede; opposite direction |
| panel | `#161b23` raised by lightness | `#ffffff` raised by lightness | same logic, inverted axis |
| accent | `#f0a92c` amber | `#926100` amber-brown | same hue family, re-levelled |
| selected | `rgba(240,169,44,0.1)` warm tint | `rgba(176,110,0,0.1)` warm tint | same treatment |

A naive inversion would have produced `#f1eee9` ground with `#e9e4dc` panels —
panels *darker* than ground — and an accent of `#0f56d3`, the hue-rotated
complement of the dark amber. Neither happened.

**The accent could not be carried across unchanged.** `#f0a92c` on white
measures **1.9:1**, far below the 4.5:1 floor. Darkening it to `#926100`
preserves the amber identity while reaching 4.74:1 on its worst surface. This is
the concrete reason FR U1-3 calls for design rather than inversion.

## Artifact: The report is generated, not hand-written

**What it proves:** The committed report and the enforced assertions cannot
disagree.

**Why it matters:** A hand-maintained contrast report goes stale the first time
someone nudges a token, and a stale report is worse than none — it looks like
evidence while asserting nothing.

**Result summary:** `contrast.test.ts` writes
`artifacts/contrast-report.md` in an `afterAll` hook from the same values the
assertions consume. Regenerating requires running the suite, and the suite fails
if any pairing is below threshold, so a committed report showing `Failing: 0` is
only producible from a genuinely passing palette.

## Artifact: ThemeContext preserved (FR U1-6)

**What it proves:** Toggling, `data-theme` stamping, and `localStorage`
persistence are unaffected by the token replacement.

**Why it matters:** The retarget touched only variable values, so the theming
mechanism should be entirely unaware of it. The strongest available evidence is
that the file was never opened for editing.

**Command:**

```bash
git diff --name-only a4d1956..HEAD -- frontend/src/contexts/ThemeContext.tsx
```

**Result summary:** Empty — unmodified across the entire branch. The same check
across `components/`, `pages/`, and `contexts/` also returns nothing, so both
themes were delivered without touching a single React file.

**Caveat:** this is static evidence. The runtime verification specified in
sub-task 2.9 — toggle the theme, confirm the attribute flips, reload, confirm it
persists — requires the running app and has not been performed. Static proof
that the mechanism is unchanged is strong, but it is not the same as watching it
work.

## Design Decision: which borders are held to 3:1

WCAG 1.4.11 requires 3:1 for boundaries needed to **identify** a control. That
scope had to be resolved before the light palette could be designed, because
applying it to every border token would force dark outlines everywhere and
contradict the spec's explicit hairline density goal.

Border usage in the stylesheet splits cleanly:

| Token | Uses | Bounds | Verdict |
| --- | --- | --- | --- |
| `--border-strong` | 16 | `select`, `input`, `.secondary-btn`, `.danger-btn`, sign-out, theme toggle | **held to 3:1** |
| `--border` | 10 | `.sidebar`, `.login-card`, `.record-card`, `.stat-card` | structural — exempt |
| `--border-soft` | 18 | card edges, table cell rules | structural — exempt |
| `--border-divider` | 4 | table row dividers | structural — exempt |

One inconsistency was found and fixed: `.sidebar-collapse-btn` is an interactive
control but drew its border from the decorative `--border` token. It now uses
`--border-strong`, keeping the categories clean. This also required raising dark
`--border-strong` from `#3d4653` (1.81:1 on a card — failing) to `#5f6b7b`
(3.19:1).

The exemption is recorded in the stylesheet, in `contrast.test.ts`, and in the
generated report, so a future reviewer sees it as a decision rather than a gap.
